# MangaDB editing baseline

Reviewed repository source and documentation on 2026-10-08. This is a code baseline, not a claim that every screen was tested in a signed-in browser. No backend or production data was changed.

## Existing functionality

- Moderators and Administrators can edit records directly; Editors submit proposals. Record pages have role-aware edit/manage links, and Edition pages link to each underlying Release's form. Release records have no separate public page. See [moderation.tsx](../../src/lib/moderation.tsx), lines 309-395.
- Direct edits require a change comment, create an approved Proposal Version, and record a public Revision. The server checks moderator access, record status and locks. The form uses a shared registry for inputs and server validation. See [moderation.ts](../../convex/moderation.ts), lines 414-459 and 596-624.
- Editable fields include Series title, alternative titles, source status, synopsis and maturity; Volume label and synopsis; Edition line position; Release binding, language, ISBNs, publication date, price and description; Publisher description; Variant name; and Bundle metadata and description. Covers and structural identities are absent from the registry. See [moderationFields.ts](../../convex/lib/moderationFields.ts), lines 7-14 and 63-135.
- Description editing already exists as plain textareas. Series and Release direct-edit pages also show source blurbs, their source links, last-seen dates, current/withdrawn markers and authorship. Human overrides protect corrections from imports, and moderators can explicitly clear an override with a reason. See [mod.edit](../../src/routes/mod.edit.$type.$key.tsx), lines 177-179, 253-255 and 450-537; [moderation guide](../moderation.md), lines 47-87.
- Public History shows each approved change's before/after values, author and role, approver, date, comment and citation. It loads when opened. Pending and rejected proposals stay private. See [moderation.tsx](../../src/lib/moderation.tsx), lines 105-208; [moderation guide](../moderation.md), lines 41-45.
- Editors can save a draft, submit for review and attach an evidence URL and note. Factual changes need evidence; editorial descriptions and synopses do not. Submission creates an immutable version. Reviewers can approve, reject or request changes, and the proposal detail shows versions, diffs, evidence and internal notes. See [mod.propose](../../src/routes/mod.propose.$type.$key.tsx), lines 214-274; [moderation guide](../moderation.md), lines 93-138.
- The review queue filters by operation, record type, author, warnings, staleness and age. Claims coordinate work without locking it. Authors have a separate proposals list. See [moderation guide](../moderation.md), lines 125-138.
- Sensitive tools already include hide, restore, merge, split and temporary locks. They show impact previews and require a written reason and confirmation. Split can undo a supported merge; it is not a generic revision rollback. Series reading-path combinations also have an undo operation. See [moderation guide](../moderation.md), lines 144-175 and 236-254.
- Some structural work has dedicated tools: the multi-record creation wizard proposes a Volume, Edition, coverage and Release together; Packaging maps an unmapped Edition to Volumes; held-book placement drafts let moderators state coverage and Edition Line. See [moderation guide](../moderation.md), lines 119-123 and 256-290.

## Description and cover inheritance

Edition descriptions are resolved from Release descriptions. With no Release text, a complete single-Volume Edition may borrow the Volume synopsis, then the Series synopsis. A Volume prefers its own synopsis, then an eligible Edition's Release blurb, then the Series synopsis. Editing the visible text therefore requires knowing which record supplied it. See [catalogPages.ts](../../convex/catalogPages.ts), lines 286-315 and 393-399.

Among Release descriptions, selection prefers a human override, an active publisher, physical format, an earlier publication date, then longer text. See [descriptions.ts](../../convex/lib/descriptions.ts), lines 27-64.

Stored cover art and importer downloads already exist. The cover downloader recognizes JPEG, PNG, GIF and WebP signatures and stores raster blobs in Convex storage; tiny images and SVG placeholders do not display as art. This is importer support, not an administrator file-upload interface. See [covers.ts](../../convex/lib/covers.ts), lines 7-25 and 103-166.

## Missing UX or constraints to address

- No administrator cover upload, drag-and-drop, paste-image, crop/preview, or cover URL replacement flow is present in the moderation forms. The field registry has no image field or input kind, and the direct form only renders those registered fields. See [moderationFields.ts](../../convex/lib/moderationFields.ts), lines 22-30 and 63-135; [mod.edit](../../src/routes/mod.edit.$type.$key.tsx), lines 216-224.
- Source blurbs are readable but have no "Use this description" control. The source panel renders plain text and source links, so the moderator must manually copy a chosen blurb into the textarea. See [mod.edit](../../src/routes/mod.edit.$type.$key.tsx), lines 450-537.
- Catalog edit entry points open a separate full-record form. There are no per-field edit controls beside the displayed synopsis, cover or publication facts in these components. Direct saves apply immediately without a before/after preview; proposal review has the diff later. See [moderation.tsx](../../src/lib/moderation.tsx), lines 309-395; [mod.edit](../../src/routes/mod.edit.$type.$key.tsx), lines 190-245.
- Public History has no generic "Restore this value/revision" action. Its body only renders revision metadata and changes. Existing restore/split/undo tools handle specific operations. See [moderation.tsx](../../src/lib/moderation.tsx), lines 137-208; [moderation guide](../moderation.md), lines 144-175 and 251-254.
- Direct-edit drafts use local React state. After the first edit, values and base Revision are pinned. If any newer Revision arrives, saving is disabled and "Reload latest" discards unsaved edits. The proposal form behaves similarly for unsaved values and override selections, while saved proposals can be explicitly rebased. There is no field-by-field conflict resolution in these forms. See [mod.edit](../../src/routes/mod.edit.$type.$key.tsx), lines 89-126 and 197-242; [mod.propose](../../src/routes/mod.propose.$type.$key.tsx), lines 88-109 and 176-197; [mod.proposal](../../src/routes/mod.proposal.$id.tsx), lines 541-579.
- Ordinary field editing deliberately excludes structural ownership, volume sort position, coverage and Release format. Existing dedicated structural tools cover specific cases; they do not form a general relationship editor for every record. Any proposal for reordering Volumes, moving Releases, editing credits or correcting relationships should describe the exact operation and preserve record identity. See [moderationFields.ts](../../convex/lib/moderationFields.ts), lines 7-14 and 63-135.
- Direct edits do not currently accept evidence attachments: the mutation stores an empty evidence list. Evidence UI exists on the Editor proposal form. A source picker or replacement-description flow should preserve its citation explicitly. See [moderation.ts](../../convex/moderation.ts), lines 414-446; [mod.propose](../../src/routes/mod.propose.$type.$key.tsx), lines 224-243.

## Cover history implementation caveat

The current internal importer attachment mutation patches `coverImage` directly and deletes old blobs when no other Release or Bundle still shows them. This mutation does not create a Revision. A future human cover replacement must use the proposal/revision path and retain previous art if cover undo is promised. Reusing this attachment mutation unchanged would lose that history. See [imports.ts](../../convex/imports.ts), lines 577-588, 612-615 and 634-659.
