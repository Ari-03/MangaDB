## Plans, as written by the architects

### Lane A: Split and merge privacy

**W01**

Root cause: three functions in convex/lib/sensitiveOps.ts treat governance per user instead of per (user, record, surface): splitScope (~1836) via addTracker/Trackers (~588-620), splitGovernance (~1941, `governing` = all Series of all records), keepSplitVisibility (~1975, `returned` x per-user `floor` on the union of fields).

Change (one shared model, no parallel implementation):
1. `type Trackers = Map<Id<"users">, Map<string, Set<VisibilityField>>>` (record id -> surfaces). `addTracker(trackers, userId, recordId, fields)`. Add `surfacesTracked(tracked)` (union of a user's sets) for the two flat consumers: carryReleaseTracking (`carryVisibility(..., surfacesTracked(tracked), ...)`) and guardSurvivorOverrides (`surfaces.includes(f)`). bundleOwners keeps using `.keys()`.
2. In trackersOf's row loop, pass the id each row was found under (seriesId for the four by_series tables, volumeId, editionId, releaseId, bundleId) to addTracker.
3. `addRefs` returns the normalized ids it added; splitScope.personal() calls `addTracker(users, userId, id, fields)` for every id of every REF_FIELD on the row (a pass is tracked on its Release and on its own seriesId, exactly as the profile gates it); the trackersOf(moved) loop copies per-record entries.
4. splitGovernance: `before: Map<recordId, Id<"series">[]>` = seriesByRecord resolved through governingSeries PER RECORD, before the replay (the replay reactivates the loser, which then governs itself); the per-user snapshot covers only the Series of the records that user tracks (dedupe per Series).
5. keepSplitVisibility: keep `after = seriesByRecord` raw for the losesSeries refusals; build `returned: Map<recordId, Id<"series">[]>` resolved now. Per user: (a) never-widen: narrowState(seriesId, [snapshot]) for each snapshot Series (unchanged rule, now limited to Series the user's tracked records answer to; a manifest-moved state row is itself a tracked record with both fields, so a merge-narrowed override is still held); (b) per tracked record r with fields f: `absorbed = absorbedFrom(before.get(r) ?? [], returned.get(r) ?? [], gate)` where gate is "one" when r is in records.editions (omnibus Ratings, see W07) and "all" otherwise; floor = absorbed.map(snapshot.get) or [null] when nothing governed; narrowState(each to-Series, floor, [...f]). `absorbedFrom` is the helper W07 adds; carryVisibility uses the same one so merge and Split share one rule (merge reads live states, Split reads the snapshot).
6. Update the comments on splitScope, splitGovernance, keepSplitVisibility and the file header: governance is tracked per record and surface; a Series absorbs only the overrides of Series the SAME tracking left.

Regression tests (convex/lib/sensitiveOps.test.ts, existing setup/box/hide/publicDefaults helpers; entry points api.sharing.setSeriesVisibility, api.collection.setReleaseEntry/setBundleEntry, api.reading.startPass, api.sensitiveOps.mergeRecords/splitRecord, api.sharing.publicProfile):
 T1 (the finding): public defaults; Source and Survivor explicitly public for Ownership, Gamma private; unowned Bundle holding Source's Release and Gamma's; user owns Source's Release directly; Volume merge Source->Survivor; expect ownership.releases length 1; Split the Volume; expect length 1 again.
 T2: same with a Series merge and Series Split.
 T3: user OWNS that Bundle and the moved Release: before and after Split, releases length 1 and bundles [] (Gamma still hides the box; the Release path is untouched).
 T4 (surface separation): Gamma private for Reading and Ownership; user owns the Bundle and has a pass on the moved Release with Source/Survivor public for Reading; before and after Split the profile lists exactly one pass (the Bundle's Ownership governance must not narrow the Reading surface).
 All four passed under the prototype. The existing 'split — never widens' and 'split — shows nothing it did not show just before' suites stay green.

Sibling variants the same root cause would leave open unless covered: Series-merge Split (T2), owned-Bundle coexistence (T3), reading-vs-ownership union of fields (T4). Standards 1 is the same change (see that finding).

Risks: The per-record floor is a refinement of the accepted wave-2 decision (Split never widens an override a merge narrowed); step (a) keeps that decision because the moved state row is itself a tracked record. The wave-2 verifier's 45,000-sequence merge/split fuzz should be rerun if the harness is still available. Trackers changes shape, but it is not exported (repair/ops.ts imports bundleOwners, carryVisibility, carryEditionTracking, editionGovernance and EditionGovernance only; verified by grep) so no signature changes leave this file.

Add `editionRatedSeries(ctx, editionId)`: the stored Edition's `editionSeriesIds` (every covered Series in coverage order, hidden Volumes and Series included, line fallback), [] if the Edition is gone. editionGovernance returns `ratedSeries: Id<"series">[]` instead of `ratedSeriesId` (EditionGovernance is only passed through by repair/ops.ts, verified by grep; tsc stayed clean).

**Standards-1**

Do not add a preflight refusal or a scheduled batch: a Split must be able to reverse any merge that itself committed in one transaction (the merge moved at least as many personal rows), and a staged Split would expose intermediate state, which the lane guidance forbids. Bound the work by design instead, which is the W01 change: (1) snapshot each user only against the Series of the records THAT user tracks (splitGovernance step 4), so lookups are Σ over personal rows found by trackersOf, each contributing one to three Series, deduped per (user, Series), instead of |users| x |Series|; (2) narrow only the Series of each user's own records (keepSplitVisibility step 5), not every `returned` Series; (3) optional write bound: before calling narrowState, group per user by (to-Series, field) the sources gathered across records and call narrowState once per (user, Series) with per-field sources (stricterVisibility is monotone, so the union of sources gives the same result), making reads and writes one per (user, Series) pair that the user's own tracking reaches. Record in the keepSplitVisibility comment that the work is proportional to the tracking rows the Split moves or re-gates, which the transaction reads regardless (trackersOf). Test: no new behavioural test; the W01 tests exercise the new loops. A verifier can assert on a fixture with N users tracking one Release each and one unowned Bundle spanning M other Series that no override is written on the M Series (the old code wrote up to N x M).

Risks: The total remains proportional to trackers in scope (a popular Series' Split reads every tracker, as its merge did). The staged form the wave-2 plan deferred (freeze both sides in sharing.ts, move, sweep, unfreeze) is still the only way past that, and stays deferred.

**Efficiency-withDependents**

Split trackersOf into its two halves: `trackersOf(ctx, touched) = { records: await withDependents(ctx, touched), trackers: await trackersIn(ctx, records) }` with a new non-exported `trackersIn(ctx, records: RecordSets): Promise<Trackers>` holding the personal-row loops. In the series merge case compute `const dependents = await withDependents(ctx, { series: [loserId] })` once, use `dependents.editions` for affectedEditions, and pass `dependents` to guardSurvivorOverrides, whose third parameter becomes `loser: RecordSets` (non-exported function) and which calls `trackersIn(ctx, loser)` only when candidates exist, so the no-candidate path reads no personal rows it did not read before. Update guardSurvivorOverrides' comment ('the loser with its dependents, read before anything moves'). No new test; the existing 'merge — Tracking Visibility of every affected User' suite covers the guard (it stayed green under the prototype). Do not stop the first traversal at Editions: the merge needs the same Release and Bundle scope for the guard anyway, and one walk is simpler than two partial ones.

Risks: None beyond keeping the walk ordered before any repoint; trackersOf and withDependents are not exported.

### Lane F: Frontend bulk-run claims

**W06**

Root cause: the claim store (src/lib/quickActions.tsx, `runClaims`, `setRunClaims`) is two plain Sets keyed only by Release id / Volume public id, so a release is anonymous: `setRunClaims(claim, false)` deletes a key regardless of which run currently holds it. `inBatches` frees per batch with `landedClaim` (correct), then its `finally` frees `claimFor(action, items)` again for every original item, which after a landedClaim release and a second run's re-acquire deletes the other run's claim. (2) Change `export type RunClaims` to `{ entries: ReadonlyMap<Id<"releases">, RunOwner>; reads: ReadonlyMap<number, RunOwner> }` and initialise `runClaims` with `new Map()`s; keep `isClaimed`, `useRunLock`, `readRunClaims` unchanged (`.has` still works; consumers in src/lib/collection.tsx:119 and src/lib/reading.tsx:239,302 use only `.has`/`.size` and need no edit — verified by `npm run typecheck`).
